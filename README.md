# Draw2Seed Research Collector v2.4 — PUBLIC

This is a **new study**, not a migration of v2.3. Deploy only this PUBLIC directory to Render. It contains **no `/dev` admin routes, raw-data browser, or record-editing code**.

## Study protocol (fixed, automatically labeled)

| Phase | Drawings | Intended use |
|---|---:|---|
| Practice | 2 | Familiarization, excluded from evaluation |
| Enrollment | 8 | All eight raw drawings stored, three reference templates selected |
| Immediate owner redraw | 6 | Genuine attempts, no displayed reference |
| Intentional near misses | 3 | Deliberate structural changes, separate attack category |
| Unrelated drawings | 2 | Wrong-shape category |
| Blind imitation | 1 | Against a randomly assigned opt-in target, if available |
| Informed imitation | 2 | Same target, with an opt-in reference displayed |
| Optional return (at least 18h later) | 6 | Delayed owner reproducibility |

The participant is shown **one task and one canvas at a time**. Labels are assigned on the server, never selected by participants. For returning participants, the site produces a high-entropy return code; its SHA-256 hash is stored in the database and the raw code is shown only once. The code is a bearer capability, not proof of identity. Participants can delete their study data.

## New verifier and comparisons

The v2.4 experimental decision rule is **2 of 3 selected enrollment templates passing the existing token + geometry verifier**, with stroke-count preservation. The eight samples are retained even if they differ. The 3 templates are selected by a token medoid and two high-agreement representatives. The system also stores: original single-reference result, token-only and geometry-only outcomes, any-reference outcome, and normalized, constrained shape DTW **distance only**. DTW has **no acceptance threshold** and is not a live authentication gate. Browser timing/pointer type are collected but **not** used to authenticate. No adaptive-gallery promotion occurs during the study.

This rule has not been proven to outperform v2.3. Do not compare v2.3 and v2.4 pooled outcomes as one test population; keep study versions separate. Do not claim raw gesture repetition provides cryptographic entropy or verified identity.

## Render deployment

1. Create a **new private GitHub repository** containing **only the contents of this PUBLIC folder**, ideally a separate Render service from v2.3 so you can roll back the previous study.
2. In Render choose **New → Blueprint** and select that repository (it contains `render.yaml`).
3. Supply `SUPABASE_DB_URL` as a **server-side** environment variable: the Supabase **Session Pooler** `postgresql+psycopg://` URL on port 5432, with `?sslmode=require`. `SECRET_KEY` is generated by Render in the Blueprint.
4. Deploy and check `/api/health`. Test a full study as a new participant before inviting volunteers. Run `/dev` only on a separate local DEV copy.

Both v2.4 packages use new `d2s24_*` database tables. **None of the old `d2s_*` rows are removed or modified.** Database table creation on startup requires sufficient PostgreSQL privileges. Use Supabase Session Pooler to avoid IPv6-only direct connection problems.

## Local test

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Edit .env: actual Supabase URL + secret
set -a; source .env; set +a
python app.py
```

This public package deliberately contains no admin module. For local administration use the **DEV ZIP** instead.

## Data handling

Consent is required before capturing drawings; sharing a reference with other volunteers is separately opt-in. Do not request real account passwords or sensitive personal drawings. Raw gestures, timing, and pseudonymous session records are research data and should be access-controlled, retained only as needed, and deleted on withdrawal. If recruiting minors, follow applicable guardian/ethics review requirements. Administrative CSV export excludes raw drawings and timing.
